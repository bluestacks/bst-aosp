# Android 16 Shared-Folder Regression Closure, 2026-08-16

Stage: Android-16 mainline maintenance

Status: resolved, published, and runtime-validated

## Scope and evidence rules

This record closes the shared-folder regression found during the restart
black-screen cycle. The investigation, build, package, and guest validation
used only the `markxu` Android-16 and app-player workspaces. It did not read or
reuse AOSP16 source or output, did not build or run A13, and did not inspect or
affect Henry's workspace or processes.

The Windows host was locked. No Windows screenshot is used as evidence. Visual
checks use guest ADB framebuffer capture; shared-folder acceptance uses exact
host-to-guest and guest-to-host byte readback.

## Superseded diagnosis

The first investigation concluded that Hyper-V selected the unavailable
`bstfolder` filesystem and that the host did not expose a maintained VBox
provider. That conclusion is preserved as investigation history in
[`restart-regression-closure-2026-08-16.md`](restart-regression-closure-2026-08-16.md),
but it is superseded by later host and runtime evidence.

The installed host Shared Folders service was loaded, and BstkVMMgr exposed
the configured `BstSharedFolder`, `Documents`, `InputMapper`, and `Pictures`
exports. The guest already contained `vboxguest` and `vboxsf`. The actual first
failure was that `mountsf` chose `bstfolder` from
`bst.status.hypervisor=hyperv` even though the available end-to-end provider
was VBox shared folders.

After selecting `vboxsf`, a real file read exposed a second defect. The guest
panicked with `UBSAN: array index out of bounds` in
`vbsf_reg_read_iter+0x8df`; the triggering process was `cat`. Disassembly and
the compiler command showed a shared `ud1` trap generated by
`-fsanitize=array-bounds`, `-fsanitize=local-bounds`, and
`-fsanitize-trap=undefined`. VirtualBox uses one-element trailing arrays in
dynamically extended request structures. Those accesses are intentional in
the imported module, but Linux 6.12's bounds instrumentation treats them as
violations.

### Review

- **Necessity:** both changes are required. Correct mount selection exposes
  the installed provider; the module guard prevents a deterministic kernel
  panic on the first real read.
- **Compatibility:** the mount behavior changes only at SDK 36 or later. The
  sanitizer guard applies only to `vboxsf` when built for kernel 6.12. A13 and
  older-kernel builds keep their existing paths and sanitizer settings.
- **Performance:** direct mounting removes one failed dispatch path. Disabling
  bounds instrumentation removes checks from this module and adds no runtime
  work, polling, allocation, or copy.
- **Security:** the change does not add exports, widen mount permissions, or
  disable sanitizers globally. It accepts the upstream module's established
  trailing-array allocation contract only within `vboxsf` on 6.12. Host
  read-only/read-write export policy remains authoritative.

The rebuilt `vboxsf.ko` contains no `ud1` instruction and its compile command
contains no `-fsanitize=*` option. Its SHA-256 is
`a5a64be8be96e81967996a34f0f4f4a782dbcf074f32edb1b68aecbde7acd777`
in the module build, HD Drivers staging, and packaged BootImage initrd.
